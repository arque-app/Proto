A parser has exactly two jobs — turn valid text into the right structure, and reject invalid text usefully. Test both, and weight the second one heavier than you'd think, because the error path is your LLM-repair surface and it's the half people under-test.

**1. Grammar acceptance — one per construct** (you mostly have this)
Each production maps to the right doc: `@meta`, roster line, `@node` block, inline edge, grouped flow, comments, blank lines. Add: multi-line `@node` with weird-but-legal values (`endpoint: https://x?a=1&b=2`), a node with no metadata, an empty `@flow`.

**2. Error path — the important half** (you have ~2, want ~15)
Every way to be wrong produces an error *at the right line* with a message that names the fix:
- undeclared node in `@flow` / in a `@node` block
- `@node` block missing `}`
- unknown directive (`@nodez`)
- malformed roster line (`A => page`, `A = `, `A = page = x`)
- `-` in an id (`user-profile = page`)
- grouped edge with no group above it
- flow line that's neither edge nor group open
- content before the first `@section`
- duplicate id in roster
Assert on **line number**, assert an error *exists* — keep message-text checks soft, wording will churn.

**3. Equivalence — things that must mean the same**
Same output for: `-->` vs `->`, `A -x> B` vs `A  -x>  B`, section order swapped, CRLF vs LF, tabs vs spaces for indent, trailing blank lines, comment-only lines interspersed.

**4. Invariants — assert on *every* result, valid or not**
- `parse()` never throws (feed it garbage, half-files, 10k random lines)
- `ok === (errors.length === 0)`
- every `edge.source`/`edge.target` exists in `nodes`
- node ids unique, edge ids unique

Short answer: **yes, and it's better than zip.** Zip is the wrong tool here, and it's worth being clear about *why* before picking the alternative.

## Why `.docx` is a zip and `.fml` shouldn't be

`.docx`, `.epub`, `.pptx` are zips because they bundle **heterogeneous** stuff — XML, PNGs, fonts, binary thumbnails. You need a container that can hold different kinds of bytes.

FML bundles **homogeneous** stuff: more FML text. Homogeneous text bundles have never needed a binary container — they use a **delimiter**:
- `.pem` files: multiple certs, `-----BEGIN CERTIFICATE-----` between them
- multi-doc YAML: `---` between documents
- `.http` / `.rest` files: `###` between requests
- git fast-import streams: plain text, many objects

The moment you zip, you lose the one property that makes FML worth having: **open it in any editor and read it.** `cat app.fml` → garbage. `git diff` → "binary files differ". An LLM can't write it without a tool. That's a bad trade for a problem a delimiter solves.

## The format: one file, many docs

```fml
@doc main
@meta
  title: ShopApp
@nodes
  Splash   = page
  Checkout = flow          # node whose body is another doc
@flow
  Splash -> Checkout
  Checkout -done> OrderPlaced

@doc checkout
@nodes
  CartReview = page
  Payment    = page
  Confirm    = page
@flow
  CartReview -> Payment
  Payment -> Confirm
```

One `.fml` file. 100% plain text. Hand-writable, diffable, LLM-writable. Parser splits on `@doc <name>` at column 0, parses each block into its own `FmlDoc`, and a node typed `flow` (or carrying `ref: checkout`) becomes a **portal** — double-click drills into that doc.
